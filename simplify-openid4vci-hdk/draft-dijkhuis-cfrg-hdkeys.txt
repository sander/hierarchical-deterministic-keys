             Hierarchical Deterministic Keys for OpenID4VCI
                   draft-dijkhuis-cfrg-hdkeys-latest

Abstract

   This document defines a small OpenID for Verifiable Credential
   Issuance (OpenID4VCI) extension for deriving many unlinkable P-256
   Credential keys from key pairs protected by a Wallet secure area.

   The Wallet sends a parent public key and an ephemeral X25519 public
   key.  The Credential Issuer generates its own ephemeral X25519 key
   pair, and both parties compute the same shared secret.  The
   Credential Issuer derives a different child public key for each
   Credential in the response.  The Wallet can use the corresponding
   child private keys with the same protections as the parent key,
   including the same user authentication mechanisms.

1.  Introduction

   A Wallet can protect one or more key pairs using a secure area.  Such
   a secure area can protect private keys against extraction and can
   require user authentication before cryptographic operations are
   performed.  Creating and storing a separate secure-area key pair for
   every Credential can, however, be expensive or impossible.

   This document defines Hierarchical Deterministic Keys (HDK) for this
   use case.  HDK enables many child key pairs to be derived from a
   P-256 parent key pair protected by the secure area.  The guarantee
   intended for a Credential Issuer is that use of a child private key
   has protections equivalent to use of its parent private key,
   including any user authentication mechanisms applied by the secure
   area.

   During Credential issuance, the Wallet and Credential Issuer
   establish a shared secret using ephemeral X25519 keys.  They use that
   secret, the parent public key, and a Credential index to derive a
   different P-256 child key pair for each Credential.  The Credential
   Issuer can derive the child public keys but never learns the parent
   or child private keys.  A Verifier only needs to understand the
   ordinary P-256 public key bound to a Credential.  It does not need to
   understand HDK.

   The material used to blind or derive keys is not a critical asset for
   the Credential Issuer's ability to rely on the Wallet.  It is
   cryptographic material used to provide unlinkability between public
   keys seen by different Relying Parties.  The security property on
   which the Credential Issuer relies remains rooted in the protected
   parent private key and the secure area's controls over its use.

   A child key pair can itself be used as a parent key pair.  The
   algebraic properties of elliptic-curve scalar multiplication make the
   same derivation and protected-use mechanisms composable across
   multiple levels.  This document specifies one issuance level;
   applications can apply the same mechanism recursively when needed.

   Related approaches include key blinding [KeyBlinding], Asynchronous
   Remote Key Generation (ARKG) [ARKG], and the mechanisms discussed for
   unlinkable Credential keys in [ETSI-TR-119-476-1].

   This document defines:

   *  an OpenID4VCI hdk proof type;

   *  hdk metadata in the Credential Response; and

   *  P-256 child-key derivation and use.

   The cryptographic specification follows the style recommendations in
   [CryptoSpec].  In particular, byte encodings, integer encodings,
   indices, and failure conditions are stated explicitly.

   This document is an early, not yet reviewed proposal.

2.  Conventions and Definitions

   The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT",
   "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and
   "OPTIONAL" in this document are to be interpreted as described in
   BCP 14 [RFC2119] [RFC8174] when, and only when, they appear in all
   capitals, as shown here.

   concat(a, b, ...) is the byte string formed by concatenating its
   arguments in order.

   bytes2int(x) interprets byte string x as an unsigned big-endian
   integer.  This is equivalent to OS2IP in [RFC8017].

   int2bytes(x, len) encodes non-negative integer x as exactly len
   unsigned big-endian bytes.  This is equivalent to I2OSP in [RFC8017].
   The operation fails if x >= 256^len.

   base64(x) is base64url encoding without padding as defined in
   Section 5 of [RFC4648].

   jwk(pk) is the JWK [RFC7517] representation of a P-256 public key.

   SerializePublicKey(pk) is the 65-byte uncompressed SEC 1 encoding of
   a P-256 public key: 0x04 || x || y, where x and y are each encoded as
   32-byte unsigned big-endian integers [SEC1].

   ScalarMult(pk, k) is P-256 scalar multiplication of public key pk by
   scalar k.

   ECDH(sk, pk) returns the 32-byte big-endian x-coordinate of P-256
   scalar multiplication of pk by sk.  Implementations MUST validate
   received public keys as required by [SEC1] before using them.

   GenerateX25519KeyPair() generates a fresh X25519 private key and
   corresponding 32-byte public key as defined in [RFC7748].

   X25519(sk, pk) is the X25519 function defined in [RFC7748], using
   private key sk and 32-byte public key pk.  It returns a 32-byte
   shared secret.  An implementation MUST reject an all-zero output.

   The P-256 group order is:

  n = 0xffffffff00000000ffffffffffffffffbce6faada7179e84f3b9cac2fc632551

3.  Credential Request

   The Wallet has a P-256 parent key pair (sk_parent, pk_parent)
   protected by its secure area. pk_parent uses the uncompressed SEC 1
   encoding when used as an input to the algorithms in this document.

   This specification assumes that, before the Credential Request, the
   Credential Issuer has already established that pk_parent represents
   the intended Credential Holder and satisfies the Issuer's security
   policy requirements.  This includes any requirements concerning the
   secure area protecting sk_parent and any user authentication required
   for use of that key.

   How the Issuer establishes this relationship is outside the scope of
   this specification.  For example, pk_parent can have been established
   as part of a PID presentation using OpenID4VP [OpenID4VP], or through
   proof of possession associated with a refresh token that is bound to
   pk_parent.  The hdk proof therefore does not introduce a new,
   otherwise untrusted parent key; it uses a parent key whose validity
   and security properties the Issuer has already accepted.

   For each Credential Request, the Wallet generates a fresh X25519 key
   pair:

   (sk_eph, pk_eph) = GenerateX25519KeyPair()

   The following non-normative example requests an ISO/IEC 18013-5 mDL
   using the Credential Configuration Identifier used in [OpenID4VCI]:

   POST /credential HTTP/1.1
   Host: issuer.example.com
   Content-Type: application/json
   Authorization: Bearer czZCaGRSa3F0MzpnWDFmQmF0M2JW

   {
     "credential_configuration_id": "org.iso.18013.5.1.mDL",
     "proofs": {
       "hdk": [
         {
           "parent": {
             "kty": "EC",
             "crv": "P-256",
             "x": "<base64url x-coordinate>",
             "y": "<base64url y-coordinate>"
           },
           "pk_eph": "<base64url 32-byte X25519 public key>"
         }
       ]
     }
   }

   The hdk proof object contains:

   *  parent: REQUIRED.  The P-256 parent public key as a JWK.

   *  pk_eph: REQUIRED.  A fresh 32-byte X25519 public key, encoded as
      base64(pk_eph).

   The Wallet MUST use a fresh (sk_eph, pk_eph) for each Credential
   Request.  The Wallet MUST retain sk_eph until it has processed the
   corresponding Credential Response.

   The hdk proof type conveys the material needed for HDK derivation.
   It relies on the Issuer having already established the identity,
   control, and security-policy properties associated with pk_parent as
   described above.

4.  Credential Response

   After accepting the Credential Request, the Credential Issuer
   validates pk_parent as a P-256 public key and generates a fresh
   X25519 key pair:

   (sk_eph_issuer, pk_eph_issuer) = GenerateX25519KeyPair()
   shared_secret = X25519(sk_eph_issuer, pk_eph)

   If shared_secret is all zero, the Credential Issuer MUST reject the
   request.

   The Credential Issuer returns pk_eph_issuer once in an hdk Credential
   Response parameter.  Credentials are ordered, and their zero-based
   position in the credentials array is their HDK index.

   For example, an mDL issuer can issue multiple mDL Credential
   instances for unlinkable presentation:

   HTTP/1.1 200 OK
   Content-Type: application/json

   {
     "hdk": {
       "pk_eph": "<base64url 32-byte X25519 public key>"
     },
     "credentials": [
       { "credential": "<base64url encoded mdoc Credential 0>" },
       { "credential": "<base64url encoded mdoc Credential 1>" },
       { "credential": "<base64url encoded mdoc Credential 2>" }
     ]
   }

   The hdk response object contains:

   *  pk_eph: REQUIRED.  The Credential Issuer's fresh 32-byte X25519
      public key, base64url encoded without padding.

   The Credential Issuer MUST bind Credential at position i to the child
   public key derived with index i.  The first Credential therefore uses
   index 0x00000000, the second uses 0x00000001, and so on.  A response
   MUST NOT contain more than 2^32 Credentials.

   After receiving the response, the Wallet computes:

   shared_secret = X25519(sk_eph, pk_eph_issuer)

   If shared_secret is all zero, the Wallet MUST reject the response.

5.  Child-Key Derivation

   Each Credential is bound to a child of (sk_parent, pk_parent).

   Define:

   HashToScalar(msg) = (bytes2int(SHA-256(msg)) mod (n - 1)) + 1

   BlindPK(pk, bk, ctx) =
       ScalarMult(pk, HashToScalar(concat(bk, ctx)))

   BlindSK(sk, bk, ctx) =
       sk * HashToScalar(concat(bk, ctx)) mod n

   HashToScalar accepts an arbitrary byte string and returns an integer
   from 1 through n - 1.  This construction has a small statistical bias
   because reduction modulo n - 1 is used.  This document accepts that
   bias for simplicity.

   For each Credential, index is the zero-based Credential position
   encoded as exactly four unsigned big-endian bytes:

   index = int2bytes(i, 4)
   ctx = concat(SerializePublicKey(pk_parent), index)

   sk_child = BlindSK(sk_parent, shared_secret, ctx)
   pk_child = BlindPK(pk_parent, shared_secret, ctx)

   where i ranges from 0 through 0xffffffff.

   Because HashToScalar never returns zero and sk_parent is non-zero
   modulo the prime group order n, sk_child is also non-zero.

   The Wallet and Credential Issuer MUST use the exact encodings defined
   in this document.  In particular, pk_parent in ctx is the 65-byte
   uncompressed SEC 1 encoding, not its JWK encoding.

5.1.  Hierarchical use

   A derived pair (sk_child, pk_child) is an ordinary P-256 key pair and
   MAY itself be used as (sk_parent, pk_parent) in another derivation.
   No special conversion is needed.

   For example, if b1 derives a first child and b2 derives its child,
   then:

   pk_child2 = ScalarMult(ScalarMult(pk_parent, b1), b2)
             = ScalarMult(pk_parent, b1 * b2 mod n)

   sk_child2 = sk_parent * b1 * b2 mod n

   The same protected ECDH and ECDSA mechanisms described below can
   therefore be applied recursively.

6.  Using a Child Key

   An implementation SHOULD arrange use of a child private key so that
   it receives protections equivalent to the parent private key,
   including any user authentication required by the secure area.

   The secure area can implement this directly by computing sk_child =
   BlindSK(sk_parent, shared_secret, ctx) internally and then performing
   the requested operation with sk_child.  Alternatively, the following
   algebraic constructions allow some secure areas to keep operating
   only with sk_parent, while processing the blinding factor outside the
   secure area.  In both cases, the secure area is expected to apply the
   same authorization policy as for use of the parent key.

6.1.  ECDH

   Let:

   b = HashToScalar(concat(shared_secret,
                           SerializePublicKey(pk_parent),
                           index))

   Then:

   ECDH(sk_child, pk) = ECDH(sk_parent, ScalarMult(pk, b))

   The Wallet can therefore multiply the peer public key by b outside
   the secure area, then perform ordinary ECDH with sk_parent.  This
   allows the secure area's existing controls, including user
   authentication, to remain attached to the parent-key operation.

   The Wallet MUST validate pk before scalar multiplication and MUST
   validate the resulting public key before passing it to an ECDH
   implementation when required by that implementation's interface.

6.2.  ECDSA

   A secure area that supports blinded ECDSA can directly compute:

   sk_child = BlindSK(sk_parent, shared_secret, ctx)
   signature = SHA256withECDSA(sk_child, msg)

   The secure area SHOULD apply the same protection and user-
   authentication policy to this operation as to signing directly with
   sk_parent.

   If the secure area cannot directly use sk_child, the following
   algebraic construction can be used with a suitable ECDSA interface.
   Let:

   b = HashToScalar(concat(shared_secret,
                           SerializePublicKey(pk_parent),
                           index))
   z = bytes2int(SHA-256(msg))

   SHA256withECDSA(sk_child, msg) is equivalent to producing (r, s * b
   mod n), where:

   (r, s) = NONEwithECDSA(
       sk_parent,
       int2bytes(z * b^-1 mod n, 32))

   Here b^-1 is the multiplicative inverse of b modulo n.  It always
   exists because b is in 1..n-1 and n is prime.

   NONEwithECDSA means ECDSA applied directly to the supplied 32-byte
   representative, without hashing it again.  Implementations MUST
   ensure that their cryptographic API has exactly this behavior before
   using this equivalence.

   The resulting (r, s * b mod n) is an ordinary ECDSA signature that
   verifies under pk_child for msg.

   The ECDSA construction described above may be covered by patent
   claims in some jurisdictions or implementations.  This document makes
   no determination about the validity or applicability of any such
   claims.  Implementers are responsible for evaluating applicable
   intellectual-property rights.  Implementing blinded ECDSA inside the
   secure area by deriving sk_child with BlindSK and signing with that
   key is an alternative architecture and can have a different
   intellectual-property analysis.

7.  OpenID4VCI Metadata

   A Credential Issuer that supports this specification advertises the
   hdk proof type in the Credential Configuration's
   proof_types_supported metadata defined by [OpenID4VCI].  For example:

   {
     "credential_issuer": "https://issuer.example.com",
     "credential_endpoint": "https://issuer.example.com/credential",
     "credential_configurations_supported": {
       "org.iso.18013.5.1.mDL": {
         "format": "mso_mdoc",
         "doctype": "org.iso.18013.5.1.mDL",
         "cryptographic_binding_methods_supported": ["jwk"],
         "credential_signing_alg_values_supported": ["ES256"],
         "proof_types_supported": {
           "hdk": {}
         }
       }
     }
   }

   The proof-type identifier is the string hdk.  Further capability
   parameters can be defined in a later revision.  Implementations of
   this early draft MUST NOT infer support for hdk merely from support
   for P-256.

8.  Security Considerations

   This specification assumes the Credential Issuer has established
   before issuance that pk_parent belongs to the intended Credential
   Holder and satisfies the applicable key-protection and user-
   authentication policy.  HDK preserves those accepted properties for
   child-key use; it is not itself the mechanism by which the Issuer
   initially establishes them.

   The intended security guarantee is inherited from the parent key: a
   child-key operation should be possible only subject to protections
   equivalent to those governing the parent key, including applicable
   user authentication.  Whether a particular secure-area implementation
   provides this guarantee is outside the cryptographic derivation
   itself and needs to be established by the Wallet's security
   architecture and evidence accepted by the Credential Issuer.

   The blinding material, including shared_secret, is not a critical
   asset for the Credential Issuer's ability to rely on the Wallet's key
   protection.  Disclosure does not by itself reveal sk_parent or permit
   use of a child private key without it.  The material is nevertheless
   privacy-sensitive because it enables relationships between derived
   public keys to be computed.  Implementations SHOULD therefore protect
   it against unnecessary disclosure and erase it when no longer needed.

   Reusing the Wallet's ephemeral X25519 key pair across requests can
   cause different issuance transactions to use related derivation state
   and can create linkability.  The Wallet therefore MUST generate a
   fresh (sk_eph, pk_eph) for every Credential Request.  The Credential
   Issuer likewise MUST generate a fresh (sk_eph_issuer, pk_eph_issuer)
   for every accepted request.

   Knowledge of shared_secret, pk_parent, and an index is sufficient to
   derive the corresponding child public key.  Disclosure of
   shared_secret can therefore reveal relationships between Credentials
   from the same response.

   The parent public key is intentionally disclosed to the Credential
   Issuer.  It MUST NOT be included in a Credential unless the
   application explicitly wants that disclosure.  Verifiers normally
   receive only pk_child.

   Compromise of sk_parent together with the issuance shared_secret
   permits reconstruction of every child private key from that response.
   Compromise of the blinding material without sk_parent does not.

   This document uses a simple biased hash-to-scalar construction.  A
   future revision can replace it with an unbiased construction if
   analysis shows that this is necessary.  Such a change would not be
   wire-compatible and therefore requires a new algorithm identifier or
   protocol version.

   The ECDSA mechanism in this document requires separate consideration
   of applicable intellectual-property rights, as noted in the ECDSA
   section.

9.  Privacy Considerations

   Different child public keys are intended to prevent Relying Parties
   from linking Credentials merely because they contain the same public
   key.  This property does not prevent linking through other Credential
   contents, protocol metadata, network identifiers, or application
   behavior.

   The Credential Issuer sees pk_parent and derives all pk_child values
   for a response.  HDK therefore does not provide unlinkability from
   the Credential Issuer.

   The blinding material exists primarily to support this Relying Party
   unlinkability property.  It is privacy-sensitive, but it is not the
   root of the Wallet key-protection guarantee.
